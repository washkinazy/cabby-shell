# Phase 3 notification design

Status: the policy, D-Bus adapter, Iced card frontend, and supervised notification unit are implemented. Audio and Bluetooth are also implemented; Phase 3 meets the documented automated/synthetic acceptance scope. No notification-specific configuration keys or D-Bus activation file are shipped.

## Scope and presentation

Provide passive text notifications with explicit action buttons and dismissal. Use the shared Iced theme. Show at most three cards on the active output, top-right below a top bar, without reserving screen area or requesting keyboard focus. A new card uses the active output when its queue slot becomes visible; existing cards retain their output. When an output disappears, move its cards to a surviving output. If no output exists, retain pending cards within the global bound and start their expiry only after presentation. Cards are at most 380×180 logical pixels, with eight-pixel gaps and margins. Dimensions shrink conservatively to fit the smallest reported output. Each entire card scrolls, including its action buttons, so bounded text remains accessible on small outputs. Each card is its own surface; gaps do not intercept input. No notification center, disk history, sounds, images, application icons, hyperlink launching, or rich-text rendering in the first feature.

The UI renders model snapshots and submits typed dismiss/action commands. Protocol logic, expiry, capacity, and replacement live in a separate Rust library with an injected monotonic clock. Passive surfaces must not intercept input outside the cards. Physical placement and pointer delivery remain explicitly unverified unless isolated automation exercises them.

## Retention and resource policy

Cabby-specific initial policy:

- Retain only active/pending notifications in memory; delete content when closed. No archive, replay, cache, or persistence across service restart. Clearing runtime state cannot recover notification text.
- Bound the combined pending/visible set to 64 entries. Reject a new entry at capacity with a resource-limit error; allow a valid replacement without allocating another slot. Do not evict a critical card silently. At most three cards are visible, with remaining entries queued in arrival order.
- Limit summary and application name to 256 UTF-8 bytes each, body to 16 KiB, and actions to eight pairs with keys/labels of at most 256 bytes each. Reject oversize or malformed requests without mutating existing state; never truncate an action identifier. Ignore unsupported hints without retaining their values. Bound the transport message/queue separately before decoding untrusted large payloads; exact library controls must be verified in implementation.
- For server-selected expiry use five seconds for low/normal urgency. Critical cards do not expire automatically. An explicit zero timeout also remains until closed. Use the protocol timeout units and sentinel values; reject values below -1. Replacement resets presentation/deadline state atomically and invalidates any old deadline token.
- Close and expiry remove an entry exactly once, even when commands race. Stale actions and old timers cannot affect a replacement. No content, action labels, or hints in diagnostics, tracing, test failure dumps, or persistent state. Fixtures use synthetic text only.

These are implementation policies, not supported configuration settings. If exposed as settings later, update the schema, reference, examples, and coverage tests in that implementation branch.

## Protocol and text policy

Implement the standard methods and closure/action signals from the [freedesktop notification protocol](https://specifications.freedesktop.org/notification/latest/protocol.html). Advertise only `body` and `actions` once both work end to end; do not claim persistence, markup, images, sound, or activation-token support. Return nonzero IDs, replace active IDs atomically, and test the specification's nonzero replacement-ID behavior explicitly. Closing an unknown ID returns an error. Close reasons distinguish expiry, user dismissal, and client closure. Actions emit the supplied key, never execute text or launch a shell. A default action is available only when supplied by the client.

Plain text is the initial rendering contract. Do not advertise `body-markup`; display supplied tags literally rather than interpreting them. The [capability contract](https://specifications.freedesktop.org/notification/latest/protocol.html) requires clients to strip markup for servers without that capability. This chooses literal display despite the [markup chapter's recommendation](https://specifications.freedesktop.org/notification/latest/markup.html) to filter unsupported tags. Preserve newlines, normalize other control characters for display, and never fetch links or files named in content.

Consume correctly typed urgency and resident hints. Unknown or wrongly typed optional hints are ignored. A resident entry remains after an action and its expiry deadline is cleared; other actions dismiss the card after emitting the action event. Transient entries already receive the no-history policy. Critical expiry follows the [urgency guidance](https://specifications.freedesktop.org/notification/latest/urgency-levels.html); hint interpretation follows the [hint reference](https://specifications.freedesktop.org/notification/latest/hints.html). These choices do not promise application activation or focus transfer.

## Ownership and recovery

Use one notification service process containing the transport, model, and Iced surfaces. This keeps the bus owner independent of bar restarts without creating an extra process for each card. The process belongs to the ordinary Cabby target and binds to the real compositor session, with cgroup cleanup and the existing bounded restart/stop policy. The coordinator starts it through `Wants=` on activation/recovery. Its own `Restart=on-failure` policy handles crashes; it is not continuously upheld, so exit 73 remains stopped on ownership conflict. No production lock coupling is introduced.

Acquire `org.freedesktop.Notifications` exclusively without replacing another owner or waiting in its name queue. An existing owner is a clear startup conflict: exit with a distinct status excluded from automatic restart, leave that owner untouched, and require an explicit retry after the conflict is resolved. Do not ship D-Bus autoactivation that could start Cabby outside its compositor-bound service lifecycle.

On session-bus loss, stop accepting requests, discard sensitive model state, and exit for bounded systemd recovery. A fresh instance reacquires the name and starts empty. No tight internal reconnection loop. Shell stop removes cards and releases the name; compositor loss stops the whole component. Ordinary bar restart must preserve notifications. A successful changed managed configuration/asset reload restarts the notification component and loses active/queued cards. Invalid or unchanged reloads preserve them.

## Implementation increments and acceptance

1. **Policy library (implemented):** typed requests/events, bounded active set, deterministic IDs, replacement, expiry, actions, and plain-text policy. Test with injected time: timeout boundaries, critical/zero timeouts, queued presentation, replacement with an old timer in flight, malformed/oversize requests, capacity with replacements, stale action keys, ID exhaustion/wrap, and exactly-once closure.
2. **Private D-Bus service (implemented as an adapter library):** pinned zbus transport with a sequential dispatcher. Test real method signatures, introspection, capabilities, errors and signals, ownership conflict, bus loss, and bounds on a private, explicitly addressed `dbus-daemon --session --nofork` owned by each test. Require explicit readiness and bounded client waits; capture no real notifications. The normal session bus must never be the integration-test target.
3. **Iced UI and lifecycle (implemented):** wire snapshots/commands into passive surfaces and ship the supervised unit. Extend isolated lifecycle fixtures for bar independence, notification crash/restart limits, name release, shell stop and compositor loss. Use nested niri with synthetic notifications for mapping, replacement without duplicate surfaces, action/dismiss state, scaling, and cleanup. Verify selected RTX 4070 Vulkan separately from tiny-skia. Synthetic output tests cover removal/reassignment; label unexercised input/hardware behavior.

Each code increment requires the standard fmt/check/Clippy/test commands. Unit changes require staged systemd verification and isolated lifecycle tests. Dependency changes must keep the Fedora installer and development reference current. Do not call the notification feature complete until protocol, UI, and lifecycle evidence all pass; do not call Phase 3 complete until audio and Bluetooth also meet their acceptance criteria.

## Policy library integration contract

`Store` is owned by one event loop. `notify` validates a complete request before changing state and returns an opaque revision-qualified `Token`. Active replacements retain their queue position; a nonzero absent replacement ID creates an entry with that same ID. Automatic IDs advance independently of client-supplied IDs, skip active IDs, and wrap past zero. Revision exhaustion rejects requests without changing state rather than permitting stale callbacks to match again.

The first three entries are presentation candidates. The UI calls `presented(token, now)` only after rendering on an available output; repeated acknowledgements do not extend expiry. Pending entries have no deadlines. After each mutation, schedule the earliest `next_deadline` as a one-shot timer and call `expire(token, now)` when due, draining additional due timers before rescheduling. No clock reads, timers, threads, or services run inside the library. The caller supplies monotonic `Instant` values from one clock domain.

UI dismissal and actions use the token from the displayed revision; protocol close uses the current numeric ID. A stale timer is a no-op, while stale UI commands return a content-free error. Emit returned action/closure events in order. Drop the store and all associated callbacks on service loss; tokens must not cross store lifetimes. Deleted strings are released, not securely zeroized; active content and caller-held snapshots remain sensitive memory.

Text limits count UTF-8 bytes before normalization. Newlines and literal markup survive; other Unicode control characters become spaces. Action keys are preserved exactly, must be nonempty and NUL-free, and cannot repeat within a request. Display labels use the same text normalization. Request, entry, action, and event debug implementations redact payloads. No unsupported hint or image data enters this library; the transport adapter handles parsing and its separate message/queue bounds.

Fourteen deterministic tests cover time boundaries, presentation and queueing, replacement/callback races, atomic rejection, byte/action limits, capacity, resident and default actions, ID wrap, revision exhaustion, deadline ordering, and redacted diagnostics. These establish policy behavior only, not D-Bus conformance or visible notifications.

## D-Bus adapter integration contract

`Service::connect(address)` requires an explicit bus address and returns only after installing its method receiver and acquiring the notification name without replacement or queueing. It returns a distinct `Conflict` error if another owner exists. The caller owns the `Service::run` future and its `Handle`; no service task is spawned by this library. Dropping the handle requests orderly shutdown. Bus loss or bounded I/O failure returns an error for the future supervisor. Shutdown and task cancellation clear the retained snapshot; caller-held copies must also be discarded. A fresh connection starts with an empty policy store. No ambient session-bus fallback or automatic reconnect exists.

The dispatcher implements the four notification methods, closure/action signals, introspection and Ping. It accepts only the notification object path and returns content-free protocol errors. No-reply calls still apply changes and emit signals but do not receive method replies. Only typed urgency/resident hints enter policy state; unsupported hints and icon fields are discarded. UI commands acknowledge presentation, dismiss a revision, or invoke a supplied action. Expiry uses one monotonic timer, with no polling loop. Snapshots coalesce in a watch channel rather than accumulating a queue of sensitive history.

The adapter defaults to an empty capability list for headless use; the Iced frontend explicitly enables `body` and `actions`. Integration tests drive the in-process UI bridge with synthetic entries; they do not establish visible notifications or real input delivery. The executable maps `Conflict` to exit 73, excluded from automatic restarts, and owns the service future as an Iced subscription.

The transport has these explicit limits:

- One queued method message and one dispatcher; no spawned task per incoming call. The connection's general queue is also set to one. UI commands have eight slots and reject overflow; action keys are checked before enqueueing.
- Reject serialized requests larger than 64 KiB before deserializing notification fields. Application text/action limits then apply. The pinned zbus reader separately rejects wire messages larger than 128 MiB before allocating their complete buffer. **The 64 KiB application limit is not a 64 KiB transport memory ceiling:** zbus can buffer larger raw messages before Cabby rejects them. This is a documented allocation limitation, not tested resistance to memory-exhaustion attacks.
- Startup, method sends, UI command completion, and signal sends have five-second limits. A command whose caller cancelled while queued is skipped; cancellation after an operation starts cannot undo an emitted action. No notification payload is included in adapter errors or logs. Do not enable third-party transport payload tracing with real notification content.

Three private-bus integration scenarios cover method signatures and introspection, malformed input and limits, atomic replacement, optional hints, capacity, exclusive ownership and no queued takeover, expiry/action/close signals, no-reply behavior, shutdown, bus loss, task cancellation and empty-state recovery. Test fixtures kill and reap their owned foreground daemon and remove the private socket directory on exit. The production user bus and notification owner are never addressed by these tests. Supervised unit fixtures and nested rendering now supply additional evidence below.

Transport references: [zbus 5.19 Builder](https://docs.rs/zbus/5.19.0/zbus/connection/struct.Builder.html), [message reader and wire bound](https://docs.rs/zbus/5.19.0/src/zbus/connection/socket/mod.rs.html), and [message queue API](https://docs.rs/zbus/5.19.0/zbus/struct.MessageStream.html).

## Running and validation

The target starts `cabby-notifications.service`, executing `cabby notifications --config %t/cabby-shell/active.toml`. The process reads the explicitly supplied session bus address from `DBUS_SESSION_BUS_ADDRESS`; a missing address is a startup error. No bus is started or discovered automatically. Normal installations require the existing niri session environment in the user service manager. Standalone supervised development can use `cabby notifications --config PATH`; do not run it against your ordinary bus unless intentionally choosing Cabby as its notification owner.

Use `systemctl --user status cabby-notifications.service` for component health. After intentionally stopping a competing owner, `systemctl --user reset-failed cabby-notifications.service` followed by `systemctl --user start cabby-notifications.service` retries ownership. Cabby never stops or replaces another notification daemon. Bar restart preserves notifications; shell stop, coordinator recovery, notification crash/restart, and compositor loss discard them. A new session starts empty.

The frontend renders literal text and action buttons with the shared theme and no keyboard focus request. A card's first redraw cycle acknowledges presentation; revision-qualified draw messages prevent a delayed frame from acknowledging a replacement. A replacement retains its window and output. Closed cards release their surfaces and promote queued entries; output removal recreates affected surfaces on an available output. No outputs means no new surfaces or presentation acknowledgements. Existing deadlines continue through output loss. Frame events are filtered to unacknowledged revisions, so they do not drive a recurring render loop after presentation. This is implementation evidence, not an idle resource measurement.

Nested tests use only synthetic notification text on a private bus. They verify rendering, replacement without duplicate surfaces, the three-card bound and queue promotion, close/expiry, passive keyboard policy, owner-conflict exit 73, and selected hardware Vulkan separately from tiny-skia. Unit tests cover stale surface events and no-output/small-output geometry. Actions and dismissal policies have private-bus and model tests; real pointer delivery, physical hotplug/multiple outputs, and accessibility interactions remain unverified. Synthetic captures do not establish those behaviors.
