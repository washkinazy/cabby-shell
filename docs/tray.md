# System tray

The bar hosts repository-owned tray UI in the desktop process. No extra daemon or GTK component is used. Cabby owns `org.kde.StatusNotifierWatcher` on the session bus when available; if another watcher owns it, Cabby registers as a host and follows its items instead of replacing it. Bus/watcher loss clears state and retries after two seconds. Desktop restarts release the watcher and menus; applications re-register with the new host.

Active items show 22-pixel icons, with attention highlighting; passive items are hidden. Left click activates the application (or opens its menu for menu-only items). If activation fails or takes more than one second, Cabby opens the item's exported DBusMenu when available. A successful activation is left to the application; Cabby cannot detect a successful no-op. Middle click invokes its secondary action, and right click opens its exported DBusMenu directly. Menus support enabled/hidden items, separators, check/radio state, and lazy submenus. Back returns to the main menu. Escape or Close dismisses the menu; opening Audio or Bluetooth also dismisses it. Without an exported menu, right click invokes the item's `ContextMenu` method. Coordinates are `(0, 0)` because Wayland does not provide global pointer coordinates here; app-owned menu placement depends on the application.

Following the local Noctalia reference, Cabby sends DBusMenu `opened` before fetching a menu and matching `closed` events when navigating away, dismissing, switching items, failing to load, or stopping the tray service normally. The root stays open during submenu navigation. Lifecycle and clicked events are dispatched without waiting for acknowledgement; successful dispatch does not prove remote execution. Root `GetLayout` starts alongside optional `AboutToShow`, which has a 500 ms deadline. A true preparation reply triggers a fresh layout; absent/error/late replies do not prevent showing the initial layout. Root preparation runs once per item/menu-path lifetime; submenu preparation runs on entry. Layout/property update signals refresh the current level without repeating preparation, avoiding exporter update loops. Forced process termination cannot guarantee closing events.

Pixmap icons use the protocol's network-order ARGB encoding. Otherwise Cabby looks for PNG/SVG icons in the item's theme path, XDG icon roots, hicolor and Adwaita size/category directories, and pixmaps directories. Absolute icon paths are supported. Missing icons show a short application label; the shared passive, opaque bar hint shows the title after a 450 ms hover, bounded to 160 non-control characters. This is a bounded lookup, not full desktop theme inheritance. Animated/overlay icons, rich tooltips, wheel actions and legacy XEmbed icons are not implemented.

The backend retains at most 64 items, accepts item property replies up to 4 MiB and pixmaps up to 512×512, and uses three-second method deadlines except for the shorter activation/preparation limits above. Menus load at most 128 entries per level from replies up to 256 KiB. Icon files are limited to 1 MiB. Commands have a bounded queue; stale owners and disabled menu actions are rejected. Snapshots coalesce and idle work is event-driven. Late worker snapshots cannot reopen a dismissed menu or replace a different item's requested menu. zbus's underlying wire-message allocation limit remains 128 MiB; semantic limits apply after transport reception. No tray payloads or menus are logged or persisted.

The tray uses shared styling and the desktop restart/reload policy in [configuration.md](configuration.md). Include `"tray"` in one bar region to enable it (the default is last in `bar_right`); omitting it from all regions disables its bus subscription. Private protocol fixtures cover rejected/timed-out activation, opened-dependent menus, lazy submenus, stalled preparation, update signals, close/reopen and failures. Nested renderer tests exercise activation fallback and paired lifecycle through the real host panel. Slack and Chromium-based ChatGPT were inspected read-only: both export valid layouts while advertising `ItemIsMenu=false`. Their live activation/actions and physical pointer behavior remain unverified.

Protocol references: KDE's [StatusNotifierItem interface](https://raw.githubusercontent.com/KDE/kstatusnotifieritem/master/src/org.kde.StatusNotifierItem.xml), [watcher interface](https://raw.githubusercontent.com/KDE/kstatusnotifieritem/master/src/org.kde.StatusNotifierWatcher.xml), and [DBusMenu interface](https://raw.githubusercontent.com/KDE/plasma-workspace/master/libdbusmenuqt/com.canonical.dbusmenu.xml).

Ordinary configuration reload now updates the existing host in place and preserves its active UI state. Renderer changes still restart it. See [configuration](configuration.md) for the current reload contract.

Item metadata reads coalesce signals for 100 ms and retry up to four attempts, with 250/500/1000 ms backoff after failure. Previously valid metadata stays visible during a failed refresh. Exhaustion waits for a new item signal/registration; owner removal clears queued retries. This handles applications that register before exporting their properties without healthy-state polling.

Theme lookup and raster decoding run in one coalesced blocking-worker batch, leaving the UI event loop responsive. Results apply only to matching current icon keys; removed owners cannot recreate items. A 64-entry recency cache includes missing icons; a missing/changed file at an unchanged key requires a restart or cache eviction. Input files are capped at 1 MiB, raster dimensions at 512×512 and decoder allocation at 4 MiB. At most 4096 candidate files are examined per lookup. The nested fixture exercises a PNG path; protocol fixtures also cover malformed/valid pixmaps, delayed exports, retry exhaustion, renewed signals and owner removal. Full theme inheritance remains outside this lookup policy.
