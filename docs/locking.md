# Locking and idle direction

Idle/lock is prioritized ahead of clipboard. Cabby's locker will have a separate compositor-bound lifetime: ordinary shell stop/restart, config reload and desktop crashes must not stop or unlock it. The existing manual locker and bindings remain in place until an explicit switch; building or installing binaries does not activate locking.

## Authentication backend (implemented)

`cabby-lock` contains UI-independent lock policy and Linux-PAM authentication. The private `cabby-auth` executable accepts one length-prefixed UTF-8 credential on stdin (1–1024 bytes), authenticates the real UID's passwd entry, and exits 0 for success, 1 for rejection, or 2 for an unavailable/malformed request. It accepts no arguments, alternate usernames, environment-selected policy, or production test mode. No password appears in arguments, logs or persistent state. The UI client allows one owned helper future with a 30-second deadline; timeout/error kills and reaps it, and cancellation kills it on drop. Helpers and PAM descendants belong to the lock service's cleanup cgroup.

The fixed policy is `/etc/pam.d/cabby-lock`, which must exist, be root-owned, and not group/world writable. Authentication and account checks must both succeed, and PAM must retain the original user. Passwordless/empty credentials and multi-step authentication are outside this initial scope; a second hidden prompt is rejected. Echoed prompts receive the fixed username. Informational/error module text is discarded. No PAM session is opened and no password-changing flow is implemented. PAM modules remain trusted system policy.

Credentials use bounded storage with redacted Debug output and explicit clearing. The helper and lock UI disable core dumps; the production lock UI removes inherited `WAYLAND_DEBUG` before accepting input because protocol traces expose physical key codes. This reduces retention but does not claim that all compiler, toolkit, kernel or PAM-internal copies can be erased. PAM owns and frees successful conversation responses. The helper is not setuid; distro PAM modules may use their existing privileged helpers.

Private tests use `pam_start_confdir` with synthetic permit/deny stacks, never a real account authentication stack. Production has no private-policy selector. Tests cover success, auth/account denial, missing modules, conversation bounds, helper framing/deadlines/cancellation, and lock confirmation/matching-attempt requirements. Real-user authentication remains unverified.

## Lock screen and lifecycle (implemented)

The lock host uses Iced's `ext-session-lock-v1` client with opaque surfaces for all outputs. READY means receipt of the compositor's `locked` event, not just a mapped window. Only a successful current authentication attempt after lock confirmation initiates a Cabby unlock. Escape clears input; it never exits. Crash, signal termination, timeout and renderer failure must disconnect without an unlock request.

The pinned exwlshellev 0.20.1 normal-exit path sends `unlock_and_destroy` when locked. Consequently the lock host must reserve `iced::exit()` exclusively for authenticated success; fatal paths use process termination and no normal-exit task. Its protocol trace must prove no unlock request on killed/failed paths. The protocol requires a compositor to remain locked after client death; replacement-locker recovery is compositor-specific and must be tested on the pinned niri baseline. If replacement is refused or restart limits are exhausted, recovery is an authenticated VT session ending the affected graphical session, not a cleanup unlock. Compositor/session loss stops the locker and its helpers.

Idle policy will use compositor idle notifications (respecting application inhibitors) and an explicit manual inhibitor. Display power must follow confirmed locking; resuming activity restores displays without unlocking. The explicit `cabby suspend` command requires confirmed lock. Observing suspend requests initiated elsewhere through logind, gamma/night-light support and hardware behavior remain separate acceptance work; automatic idle locking is opt-in through the timeout below.

References: [session-lock protocol](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/staging/ext-session-lock/ext-session-lock-v1.xml), [idle notification protocol](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/staging/ext-idle-notify/ext-idle-notify-v1.xml), [Linux-PAM ABI](https://raw.githubusercontent.com/linux-pam/linux-pam/master/libpam/include/security/_pam_types.h), [systemd restart semantics](https://www.freedesktop.org/software/systemd/man/262/systemd.service.html), [PAM initialization/private policy directories](https://raw.githubusercontent.com/linux-pam/linux-pam/master/doc/man/pam_start.3.xml).


### Installation and use

After `just install`, run `just install-lock-support` to install the Fedora `system-auth` PAM include and the local user unit. This explicit task requires sudo for the system PAM policy; it refuses differing existing policies/units, never enables or starts a service, and leaves all bindings unchanged. The regular install task only installs binaries. Other distributions need a reviewed distro-appropriate PAM stack; the supplied policy targets Fedora.

`cabby lock` starts `cabby-lock.service` and waits for compositor confirmation through systemd READY. It requires an active `niri.service` but does not require the ordinary Cabby shell target. Repeated requests use the existing instance. An explicit `cabby lock` request resets the unit start counter before starting, so rapid successful lock/unlock cycles do not exhaust the automatic recovery budget. Test/service overrides are `--lock-unit NAME.service` and `--session-unit NAME.service`. `cabby lock-ui [--config PATH]` is the unit entrypoint, not a standalone supervision replacement. There is no unlock command.

The full-output opaque UI accepts keyboard password entry, Enter to authenticate, Backspace, Escape/Ctrl+U to clear. Clipboard, password reveal and account selection are absent. Credentials entered while securing the session or checking a password are ignored. Authentication errors keep the UI locked and permit retry. Shared renderer/font/colors apply on the next lock; config reload cannot restart an active locker. Invalid styling configuration uses built-in defaults so an unrelated edit cannot block locking; failure to resolve the config path or initialize the renderer still fails closed. Missing/untrusted PAM policy or missing helper fails before acquiring a lock.

The unit binds only to the compositor, has control-group cleanup, disables core dumps, refuses manual stop, and allows three starts per 120 seconds with a one-second restart delay. Acquisition must confirm within 12 seconds (systemd startup limit 15 seconds). Competing-lock denial exits 73 without restart. Unexpected termination signals and other crashes restart within that bound; niri's orphaned-lock replacement is exercised in the disposable compositor. Ordinary shell stop/restart/reload does not touch the locker. Ending the compositor session stops it. A successful authentication exits normally without restarting. Exhausted recovery requires an authenticated VT session to end the affected graphical session. Cabby fatal/termination cleanup does not request unlock. The trusted compositor may independently end lock ownership with `finished` (for example after its own secure authentication); the pinned library acknowledges that protocol event with `unlock_and_destroy` if already locked, and Cabby exits without another unlock or restart. That compositor-driven path is distinct from a client failure and is not exercised by the niri fixture.

### Evidence and boundaries

`python3 scripts/test_lock_session.py --renderer gpu` (or `software`) runs the real host with an explicitly injected synthetic credential verifier in a guarded private niri session. It checks READY after confirmation, buffer attachment, competing-lock rejection, scale change, wrong/correct credentials, signal/fatal exits without unlock, and replacement after orphaned-locker death. `python3 scripts/test_lock_lifecycle.py` tests the shipped unit with a notify-aware stand-in for READY gating, duplicate ownership, ordinary-shell independence, restart bounds and session cleanup. Private PAM tests independently exercise the real PAM adapter. This does not establish real-user authentication, physical input/multiple-output coverage or DRM lock security; existing daily lock bindings have not been replaced. Automatic idle locking is opt-in as described below; night light remains unimplemented; opt-in display and external sleep policies are described below.

## Keyboard indicators

The locked view shows the active keyboard-layout name and a warning when Caps Lock is on. Both come from Wayland seat modifier/keymap state, including the initial focused state; Cabby does not infer Caps Lock from typed characters or toggle it. Keyboard leave clears the indicators to unavailable until new seat state arrives. Layout names are bounded and stripped of control characters. These messages never alter the credential buffer, authentication attempt or unlock policy.

The pinned Wayland binding needs a small repository patch to preserve this information through Iced's shell-event channel; provenance and the exact patch surface are recorded in [vendor/README.md](../vendor/README.md). No extra daemon, polling or permissions are added. Synthetic tests check Caps Lock/state changes without credential/policy changes; nested tests change the compositor's keyboard layout. Physical Caps Lock input, multiple seats and real-user authentication remain unverified.

## Explicit lock-before-suspend

`cabby suspend` first verifies the compositor session, starts the independent locker and waits for its compositor-confirmed READY, then rechecks both the session and locker before submitting a suspend request. It uses the same optional `--lock-unit NAME.service` and `--session-unit NAME.service` overrides as `cabby lock`; overridden units must retain the shipped notify/readiness and compositor-binding contract. It works independently of the ordinary shell target and uses an already active locker without restarting it. Install lock support before using either command.

A missing session, failed lock, missing readiness or failed post-lock check prevents submission. Queries/reset have five-second deadlines, lock startup has a twenty-second client deadline (the shipped service has a fifteen-second startup limit), and suspend submission has a ten-second deadline. Owned systemctl clients are killed/reaped on timeout and killed if the CLI dies. An already accepted systemd job may still complete after a client timeout; Cabby never stops or unlocks the locker as cancellation or error cleanup.

The suspend request uses `systemctl --no-ask-password --check-inhibitors=yes --no-block suspend`: existing system sleep inhibitors and authorization policy apply, with no authentication prompt or inhibitor override. Rejection returns failure and leaves the session locked. Success reports request acceptance, not proof of sleep or resume. Activity after resume does not authenticate/unlock the locker. The readiness check and power request are separate operations; an authenticated unlock or compositor termination between them is not atomically prevented. Optional logind delay-inhibitor observation is described below; it does not make readiness and suspend atomic.

The CLI fixture tests intercept every systemctl call and cover absent/lost sessions, lock rejection, readiness failure, locker exit, inhibitor/authorization rejection, argument handling and request order. The systemd lifecycle harness additionally waits for a real notify test unit, substitutes only the final power request, and verifies rejected suspend leaves the same locker instance active. No host suspend, live locker, real inhibitor or hardware resume is exercised. Neither installation nor this implementation changes existing lock/suspend bindings.

## Automatic idle locking

Set `idle_lock_seconds = 600` to lock after ten minutes of inactivity; the default `0` disables observation. Install lock support first. The coordinator owns a Wayland worker using `ext_idle_notifier_v1.get_idle_notification`, which respects compositor application inhibitors. All advertised seats must be idle. No command polling measures inactivity. A completed or failed request fires once per idle cycle; new activity permits a later request. Connection loss clears old state and retries after two seconds; absent protocol/seat reports `unsupported`.

Use `cabby idle-inhibit-on`, `cabby idle-inhibit-off` or `cabby idle-inhibit-toggle` for a coordinator-lifetime manual inhibitor, and `cabby idle-status` to inspect the timeout, inhibitor and backend status. These accept `--runtime-dir PATH` for isolated coordinators. Explicit locking/suspension is unaffected. Changing the timeout or releasing inhibition starts a new full countdown. Inhibition/reconfiguration cancels owned request clients, but an accepted systemd job can still complete and is never unlocked as cleanup. Automatic suspend and external logind coordination remain separate work.

`python3 scripts/test_idle_session.py` exercises real notifications in a disposable niri and intercepts every systemctl operation. It verifies one request per idle cycle, manual inhibition/release, fresh timers on reload, invalid config retention and disable. The test cannot activate a real locker or suspend the host. Physical application-inhibitor behavior and multiple seats remain unverified; protocol semantics and synthetic lifecycle coverage are distinct from real-hardware acceptance.

The optional `idle` bar contribution shows lock/inhibition state and toggles the same manual inhibitor. Add it to a bar region; it is omitted by default. Pending clicks are coalesced; a failed request displays an action error and permits retry. Runtime snapshots are bounded/atomic and watched rather than polled. Desktop restarts retain the coordinator-owned inhibitor.

## Display power

`cabby display-off` confirms locking through the independent locker, rechecks its session and requests niri DPMS power-off. `cabby display-on` restores power without unlocking or requiring the locker. Commands use explicit arguments and owned five-second clients, never output removal or a shell. A rejected lock prevents the power request. Success means IPC acceptance, not physical monitor behavior.

For automatic power-off, set `idle_display_off_seconds` greater than positive `idle_lock_seconds` (for example 660 after 600). The display deadline independently requires confirmed locking even if the earlier idle-lock attempt failed. It shares application/manual inhibitors and all-seat idle gating. Activity restores power; inhibition, config changes, seat/idle-manager registry changes and graceful observer cleanup restore any possibly submitted display action before resetting timers. A failed restore is reported through stderr/status, without retry loops or unlock. Abrupt coordinator loss cannot run Rust cleanup; niri's own [input wake behavior](https://github.com/niri-wm/niri/discussions/1114) and explicit `cabby display-on` are the recovery paths. This remains unverified on real monitors.

The native idle harness intercepts both lock and niri helpers, checking timeout ordering and inhibition-driven restoration. CLI fixtures verify lock failure prevents DPMS and restoration does not request unlock. Tests never power down the user's monitor. Hardware DPMS, hotplug and wake behavior remain unverified. The lock itself keeps its independent lifetime throughout.

## External sleep coordination

`lock_before_sleep = true` lets the coordinator hold logind's sleep delay inhibitor. It subscribes to the current unique logind owner before acquiring the FD, observes PreparingForSleep, and attempts `cabby lock` on PrepareForSleep(true). The FD is retained until confirmed readiness or the bounded attempt ends. Duplicate true signals do not create duplicate clients; signals from unrelated senders are ignored. Resume cancels pending clients, resets idle/display timers and obtains a fresh lease. Bus/owner loss releases owned work and reconnects; disabling the setting cancels it. Lock jobs already accepted by systemd remain independently supervised and are never unlocked as cleanup.

This is a finite delay, not a sleep veto: logind can proceed when its own deadline expires, including after lock failure. Cabby reserves 100 milliseconds of the advertised delay (maximum client wait 30 seconds), reports failed/unavailable state, and does not claim that late startup or real hardware suspend is safe based on fixtures. Use the explicit `cabby suspend` path for confirmation before initiating Cabby's own request. No UI, unit, service installation or default activation is added.

A private D-Bus Manager fixture returns real caller-owned FDs. It checks that leases remain open while waiting, close after readiness/timeout, are reacquired on resume and released on owner loss; unrelated signal senders cannot start locking. Fixture helpers provide readiness or hang until cancellation. No system bus ownership, host power operation, live locker or account authentication is exercised.
